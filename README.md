# CLAUDE_Game — плагин `studio` для Claude Code

Проектный процесс для одного владельца и двух чатов. Вырос из разработки игры
Asterworn и обобщён: годится для игры, приложения, сервиса — любого проекта,
где один человек придумывает и принимает работу, а Claude пишет код.

## Что он делает

- **`/setup`** проверяет компьютер (движок, версии, недостающее ставит через
  winget после «да»), разбирает принесённые образцы до вопросов, спрашивает
  окнами только о решениях владельца, **сам придумывает, как проверять этот
  продукт на этом стеке**, разворачивает `CLAUDE.md` и `docs/`, ставит очередь
  вертикальным срезом и в конце запускает первое окно игры. В проекте с кодом
  — сначала читает код.
- **Вид — картинками, а не словами.** Названная игра, скрин, «как в X» —
  разбор образца в `docs/refs/`; пункт `[вид]` делается 2–4 вариантами рядом с
  образцом, и выбирает владелец по листу сравнения, а не проверяющий.
- **Два чата в одной папке.** Чат замысла меняет только `.md` и картинки-образцы
  в `docs/refs/` и никогда не запускает продукт; чат разработки пишет код руками субагентов. Разделяет их
  не ветка, а то, что каждый трогает.
- **Список — не наряд на работу.** Всё входящее сначала разбирается и встаёт в
  одну очередь в `docs/ROADMAP.md` по влиянию на пользователя — со словами
  владельца дословно.
- **Исполнитель → проверяющий, не больше трёх кругов**, контрольный коммит
  после каждого одобренного пункта. К каждому пункту — «Как увидеть» (где в
  продукте смотреть) и «Решено за вас» (что агент решил сам); снимки снимаются
  там, где будет смотреть владелец.
- **Принимает только владелец** — `/done`: непринятое откатывается
  revert-коммитом, причина отказа записывается его словами.
- **Вопросы — окнами.** Выбор владелец делает в диалоговом окне, а не
  отвечает текстом в чат.
- **Заказы промтом.** Графика, 3D-модели, текстуры, музыка, звук, макеты,
  тексты: стиль записан один раз в `docs/orders/<вид>.md`, заказ собирается из
  документа, ложится в файл и долгом в `BLOCKED.md`. Исполнитель — вручную,
  OpenAI API или Claude Design. Пришедший файл сначала проверяет скрипт, брак
  уходит в перезаказ; откуда ассет и какие на него права — в журнале прав.
- **Игру проверяют так, как в неё играют.** Управление, интерфейс и действия
  игрока — сценарием через ввод: он нажимает, как игрок, а не вызывает
  функцию.
- **Выпуск — `/release`.** Сборка, проверка собранной версии, тег, заметки
  словами игрока, титры из журнала прав; itch.io и бета Steam — только по
  «да» владельца.
- **Дизайнер в конвейере.** Пункт с меткой `[ui]` сначала получает спецификацию
  экрана от субагента `designer`, а проверяющий сверяет снимок экрана с ней.

## Установка

```
/plugin marketplace add Metalismaticus/CLAUDE_Game
/plugin install studio@claude-game
```

Обновление: `/plugin marketplace update claude-game`. Проект, развёрнутый
прошлой версией, — `/setup обновить`: сравнит процессные разделы документов с
шаблоном (по метке `шаблон vN` в `CLAUDE.md`), покажет разницу и по согласию
заменит только их; стек, правила проекта, очередь и записи не трогает.

Затем в папке проекта — `/setup` (полное имя `/studio:setup`; короткие имена
работают, пока не заняты другой командой: поэтому дефект — `/fault`, макет —
`/mockup`; что переименовано между версиями — в `CHANGELOG.md`).

## Команды

| Команда | Чат | Что делает |
|---|---|---|
| `/setup [обновить]` | любой | развернуть процесс в проекте (один раз) или перенести в него новый шаблон |
| `/idea <заметки>` | замысла | разобрать, сверить с кодом и историей, решение — окнами, разнести по документам; игра, скрин, «как в X» — разбор образца |
| `/fault <симптом>` | замысла | записать дефект с местом (экран, seed, координаты), причиной и строкой «нельзя ломать»; не чинить |
| `/order <вид> <что>` | замысла | собрать заказ, записать долг, отправить исполнителю; `/art`, `/music`, `/mockup` — короткие формы; `art кадр-цель` — перерисовка нашего кадра под образец |
| `/need [раздел]` | замысла | все долги владельца: заказы с готовыми промтами, решения — окнами |
| `/start [пункт\|all]` | разработки | выполнить очередь; «делай» и «делай всё» значат то же |
| `/done [кроме…\|только…]` | разработки | принять партию или её часть окнами, остальное откатить |
| `/add [папка\|design]` | разработки | принять пришедшие файлы заказов и макеты |
| `/check [имя]` | разработки | прогнать проверки и разобрать провалы; упавшую быструю — повторить до трёх раз |
| `/parallel [N\|проверки M\|проверить]` | разработки | сколько пунктов пишется разом (0/1 — по одному, 2, 3, 4 …) и сколько тяжёлых проверок идёт разом; проверить пробным прогоном |
| `/retro` | разработки | уроки партии и причины отказов: проекту — в документы, процессу — в `docs/PLUGIN-FEEDBACK.md` |
| `/release [версия] [itch\|steam]` | разработки | выпустить версию игры: сборка, проверка собранной версии, тег, заметки, титры; выкладка — по «да» |
| `/board` | любой | один экран: что ждёт вас, партия, очередь, неладное; только чтение |

`/setup`, `/add`, `/check`, `/parallel`, `/retro`, `/release`, `/art`,
`/music`, `/mockup` зовёт только владелец: Claude сам их не запускает.

Субагенты: `executor`, `reviewer`, `designer`, `scout`, `assets`, `reference`
(разбор образца вида; зовут `/idea` и `/setup`).

## Новый проект: `/setup`

Короткий порядок в `skills/setup/SKILL.md`, подробности шагов — в
`skills/setup/steps/`. Быстрый старт (по умолчанию) или подробно:

1. «Расскажите своими словами и принесите всё, что есть» — игры, скрины
   (можно вставить в чат), ссылки, заметки.
2. Проверка компьютера (`plugins/studio/tools/env_check.ps1`, только чтение):
   ОС, видеокарта, движки и их версии, git, python и Pillow, gh, winget.
   Недостающее — отдельный вопрос на каждую программу (до четырёх в окне),
   установка через winget только после «да». Итог — «Окружение» в
   `docs/TESTING.md`; факты владельцу не задаются как вопросы. Движок новее
   знаний модели или стек незнаком — предложит плагин **Context7**
   (документация ровно этой версии; ставит владелец сам: **+** у поля ввода →
   Plugins → Add plugin → context7).
3. Разбор до вопросов: на каждый названный образец — агент `reference`,
   параллельно.
4. Раунды окон: жанр и камера; 30-секундный цикл; что берём у образцов,
   главный образец, стилизация; стек (с «пробой стека», если ядро упирается в
   производительность); исполнители заказов и приватность репозитория. Для 3D
   — правила масштаба и осей.
5. План в `docs/SETUP-PLAN.md` (не коммитится) — окно «Принять / Поправить».
6. Документы, `docs/refs/`, `.gitattributes`. Очередь — вертикальным срезом:
   каркас → проверки и стенд вида → «серая коробка» → первый кадр по образцу →
   полный цикл на 3–5 минут; у каждого пункта «Как увидеть».
7. Каркас проекта в движке и запуск окна игры; снимок —
   `docs/refs/setup/first-frame.png`. Не запустилось — причина записывается, а
   не скрывается.

Каждое решение и допущение — строкой в `DECISIONS.md`, «Старт»: повторный
`/setup` показывает, что меняется, а не переписывает документы.

## Образцы вида и пункты `[вид]`

- `docs/refs/INDEX.md` — главный образец, шкала стилизации, темы;
  `docs/refs/<тема>.md` — паспорт образца: слова владельца дословно, образцы,
  составляющие (как у образца, чем доказано, важно ли владельцу, как сделано
  в той игре), именованные кадры, проверяемые утверждения, журнал выбора;
  картинки — в `docs/refs/<тема>/`. Образцы лежат в git (репозиторий
  приватный; публичный — чужие кадры в `.gitignore`, в паспорте ссылка).
- Агент `reference` копирует картинки владельца, находит 3–6 кадров именно
  этого предмета в названной игре, ищет, **как это сделано в этой игре**
  (доклады, блоги студии, разборы кадра), раскладывает по составляющим и
  называет противоречия. Что главное — владелец отвечает окном.
- `[вид]` — вода, растительность, свет, небо, туман, материалы, эффекты,
  облик персонажей (`[ui]` — только экраны интерфейса). Условия: паспорт
  подтверждён, картинки на месте, в `docs/TESTING.md` «Стенд вида» — `есть`.
  Исполнитель делает 2–4 варианта, снимает на кадрах паспорта и собирает лист
  сравнения (`tools/look_sheet.py`, нужна Pillow); проверяющий смотрит
  сначала картинки и пишет «готово к выбору владельца»; владелец выбирает
  окном, ≤ 3 кругов, затем выбранное встраивается в мир, принятый кадр —
  `accepted-<дата>.png`.
- Порядок работы над видом: свет, туман и цветокоррекция → силуэт и масса →
  материал или шейдер и движение.
- Все ли картинки на месте — `tools/refs_check.py`; его зовут `/need` и
  `/board`.

## Вопросы и приёмка

Правила вопросов — `plugins/studio/reference/ASKING.md`, команды с вопросами
ссылаются на него. Выбор — окном (рекомендуемый вариант первым) и только о
решениях владельца: замысел, вкус, приоритет, приёмка, деньги, необратимое;
технику агенты решают сами и пишут строкой «Решено за вас». Субагент окно
открыть не может — пишет «Вопрос владельцу», окно показывает координатор; в
`/start all` вопросы задаются в конце партии. Окна нет — тот же вопрос списком.

`/done` спрашивает окнами, что принимается и что не так с непринятым; причина
записывается в `ROADMAP.md` (у бага — в `BUGS.md`) дословно со снимками. До
принятия он показывает замечания владельца из чата замысла; «Решено за вас»
можно оспорить — оспоренное идёт в поправку.

## Параллельная работа

`/start all` пишет независимые пункты одновременно, каждый в своей копии
проекта (git worktree `../<папка>.wt/slot<K>`, копии переиспользуются), и
вливает их в `main` по одному. Что идёт вместе, решает разведчик `scout`:
файлы не пересекаются, общих узлов (конфигурация, схема данных, миграции,
реестры, lock-файлы) нет, пункты не зависят друг от друга и не меряют
производительность. Сомнение — по одному.

**Пишем параллельно, тяжёлая проверка одна.** Проверяющий каждого пункта в
`/start all` работает в лёгком режиме (diff, проверка пункта, её группа,
быстрая); полная и долгая проверки — один раз в конце партии. Покраснело —
виновник ищется делением пополам по коммитам пунктов и откатывается на
следующий круг. Одиночный `/start` гоняет полную сразу.

Настройки в `docs/TESTING.md`: **пишут** — сколько пунктов разом
(`/parallel 4`, на один запуск `/start all x4`, `/parallel 0` — по одному) и
**тяжёлых проверок** — сколько полных прогонов разом (`/parallel проверки 1`).
Предел — потолок, а не план; `/parallel проверить` меряет его пробным
прогоном. Пока копия не «проверено» — всё по одному.

Не влилась копия или проверки начали врать — пункт переделывается по одному.
Два пункта споткнулись об одно и то же — похожие ждут, пока пробел не закрыт.
Партия оборвалась — `/start` продолжает по `docs/BATCH.md` и коммитам
`Пункт N:`, а не по памяти. Ускоряет это код, а не проверку владельцем.

## Маршруты пунктов

| Метка | Путь |
|---|---|
| `[код]`, `[баг]` | `executor` → `reviewer` с полной проверкой (в `/start all` — лёгкой, полная в конце партии) |
| `[вид]` | `executor` (2–4 варианта на стенде вида и лист сравнения) → `reviewer` по картинкам → выбор владельца окном; в `/start all` выбор — в конце партии |
| `[ui]` | только экраны интерфейса: `designer` → `executor` → `reviewer` со снимками экрана и сверкой со спецификацией |
| `[данные]` | `executor` → `reviewer` без полной проверки |

Пункт `[вид]` без подтверждённого паспорта образца стоит `[ждёт образца]`.
Критерий пункта другой метки про вид — снимки нужны всё равно: место из «Как увидеть»
или записи бага и канонические ракурсы. Без снимка, когда снять можно, такой
пункт не одобряется; снять нечем (в `docs/TESTING.md` нет команды снимка) —
одобрение с пометкой «вид не проверен», вид смотрит владелец.

Незнакомый API движка или библиотеки исполнитель берёт из документации ровно
этой версии (Context7, если подключён; иначе `docs/engine-notes.md` или
официальная); расхождение с памятью модели — строкой «Ловушка».

## Сценарии игрока

Для игр; продукту без игрока раздел в `docs/TESTING.md` — «не нужен». Пункт
про управление, интерфейс или действия игрока проверяется сценарием
`tests/scenarios/<имя>.json` (или ресурсом движка того же смысла): точка
входа, зерно, фиксированный шаг, шаги `press` (действие ввода, кадр, сколько
держать), `wait_frames`, `wait_for` (объект или текст, предел в кадрах),
`assert` (свойство или текст на экране: `equals`, `min`, `max`; `within` /
`always` — хоть на одном или на каждом из N следующих кадров), `shot`
(снимок). Утверждения — по именам и группам объектов, кнопки интерфейса
нажимаются по тексту, а не по координатам; время — в кадрах. Раннер входит в
полигон: код 0 — зелено, 1 — провал (какое утверждение, на каком кадре, какие
действия остались зажаты), 2 — плохой сценарий.

`/setup` ставит в очередь раннер сценариев и сценарий главного действия ядра,
который краснеет, если сломать управление (в новом проекте — кусок «Серой
коробки»); полная проверка гоняет все сценарии. Проверяющий смотрит, что
сценарий нажимает, а не вызывает. «Готово, когда» можно писать шагами игрока —
это текст сценария. Зонд, понадобившийся второй раз, становится проверкой или
сценарием.

## Исполнители заказов

| Исполнитель | Для чего | Что нужно |
|---|---|---|
| `вручную` | всё | ничего: промт выдаётся одним блоком |
| `api` | графика | `OPENAI_API_KEY` в окружении и Python; платно, отдельно от подписки ChatGPT. Стиль держат приложенные образцы — каждый запрос сам по себе |
| `claude-design` | макеты экранов | настольное приложение с входом в claude.ai. Плагин выгружает дизайн-систему проекта и готовит бриф; **генерацию запускает владелец** — поставить задачу в Claude Design извне нельзя; готовый макет забирает `/add design` |

Ключи и пароли плагин не спрашивает и в файлы не пишет. Автоматика не
сработала — заказ остаётся обычным долгом с готовым промтом.

3D-модели (`model3d`: glTF/GLB, масштаб по росту персонажа, опорная точка,
«вперёд», бюджет треугольников, LOD, простые столкновения) и текстуры
(`texture`: бесшовность, карты PBR, плотность текселей) сначала ищутся в
бесплатных библиотеках CC0 (Kenney, Quaternius, Poly Haven, ambientCG);
платное — только после «да». Подвид графики «кадр-цель» перерисовывает наш
кадр так, чтобы одна составляющая стала как на образце: это направление, а не
пиксельная цель.

Не сделано намеренно: заказ через Codex CLI и через автоматизацию веб-интерфейса
ChatGPT. Первое не проверено, второе хрупко и не одобряется правилами сервиса.

**Проверка пришедшего.** `/add` и агент `assets` до осмотра глазами
запускают `tools/asset_check.py <файл> [--canvas WxH] [--alpha
required|none|any] [--pixel-art] [--json <file>]`. Картинка: холст против
заказа, альфа и доля прозрачного, прозрачные углы, нарисованная «шахматка»
вместо прозрачности (частый брак генераторов), фон не вырезан или объект
упёрся в край — это разные сообщения: перезаказ с другим фоном или с полями
от краёв; у пиксель-арта — число цветов и шаг сетки. Звук: длительность,
каналы, частота, клиппинг, тишина в начале (WAV; у OGG — только заголовок).
Код 0 — годен или «поправить» (холст больше в тех же пропорциях, тишина в
начале, лишние цвета пиксель-арта от генератора — `/add` поправит и проверит
снова); 1 — брак: как пришедшее не записывается, уходит из проекта и строкой
«перезаказать: <почему>»; 2 — не умеет, нет файла или Pillow. У графики в
паспорте вида — столбец «Размер в игре» (пикселей на экране, метров, шаг
тайла): без него `/order art` заказ не собирает, меньше 128 px — заказывается
лист из нескольких объектов. `order_api.py` пишет файл атомарно и после
прозрачного фона проверяет альфу.

## Журнал прав на ассеты

`docs/orders/ledger.md` — откуда каждый ассет: файл, вид, исполнитель или
сервис, тариф на момент создания, дата, заказ, лицензия, атрибуция,
ИИ-контент (`да/нет` — для раскрытия в Steam: заранее созданное ИИ, что игрок
видит или слышит), состояние. `/order` пишет строку при отправке, `/add`
дополняет при приёме; библиотеки CC0 — «CC0, атрибуция не нужна».

У музыки с бесплатного тарифа генератора права некоммерческие, и платная
подписка задним числом их не даёт: `/order` спрашивает тариф окном, если он
не записан в паспорте вида; лицензию — по условиям сервиса для этого тарифа.
В счёт идёт последняя строка `принят` каждого файла в git: заменённое и
удалённое не считается. `/board` показывает «ассеты с некоммерческими
правами: N», `/release` их не выпускает.

## Выпуск игры: `/release`

Команда чата разработки, вне партии; зовёт только владелец.

1. Условия: партия пуста, ветка чистая, полная проверка зелёная на этом
   коммите (нет — прогоняется), в журнале прав нет некоммерческих ассетов;
   ассеты без записи о правах — окном, до сборки.
2. Сборка — строкой «сборка» из `docs/TESTING.md` (у Godot —
   `--headless --export-release`, шаблоны экспорта ровно под версию движка).
3. Проверка **собранной** версии, а не редактора, — строка «проверка сборки»:
   запуск собранной игры на N кадров или сценарий игрока.
4. Номер — окном с рекомендацией от прошлого тега (исправления / новое /
   большое); тег `v<версия>`.
5. Заметки `docs/releases/<версия>.md` словами игрока из «Сделано» с
   прошлого тега, принятые кадры образцов.
6. `CREDITS.md` из журнала прав и черновик раскрытия ИИ-контента для Steam.
7. Выкладка — по «да» окном на каждую площадку: itch.io — `butler push <папка>
   <user>/<игра>:<канал> --userversion <версия>`; Steam — SteamCMD
   `+run_app_build` на **бета-ветку**, ветку по умолчанию переключает
   владелец. Вход в butler и SteamCMD владелец делает сам: плагин только
   проверяет, что вход есть, и не ждёт пароля; паролей и ключей не касается,
   имя аккаунта Steam в файлы не пишет.
8. Отчёт и строка в `docs/DECISIONS.md`, «Выпуски».

Пресеты, папка сборки и площадки — в `docs/TESTING.md`, «Выпуск». Продукт не
игра — шаги площадок и раскрытия ИИ пропускаются.

## Хуки

Работают во всех чатах папки. Нужен Python в `PATH`; без него хуки молчат.

- **`guard_git.py`** — перед командами Bash и PowerShell, только в проектах,
  развёрнутых `/setup` (есть `docs/BATCH.md`). Останавливает то, что берёт или
  стирает всё разом: `git add -A | --all | -u | .`, `git commit -a`, любой
  `git stash`, `git clean`, `git reset --hard`, `git checkout .`,
  `git restore .`, переключение с `-f`, `git push --force` (`-f`,
  `--force-with-lease`). В папке два чата, у чата замысла бывают
  незакоммиченные `.md`. `reset --hard`, `clean` и переключение с `-f`
  разрешены в копиях `*.wt/…`, `git checkout -- <файл>` поимённо — везде.
  Модель получает объяснение и что делать вместо.
- **`session_context.py`** — при начале, продолжении, очистке и сжатии сессии:
  идёт партия — напоминает продолжать по `docs/BATCH.md` и `git log --grep
  "Пункт"`, а не по памяти.
- **`selftest.py`** — самопроверка: `python -X utf8
  plugins/studio/hooks/selftest.py` подаёт хукам пробные события (кириллица и
  пробелы в путях), печатает таблицу; код 0 — всё верно. Её зовут `/board` и
  `/setup` («страж коммитов: работает | молчит»).

## Устройство

```
.claude-plugin/marketplace.json
CHANGELOG.md
docs/WHY.md    почему процесс устроен так — прочитать, прежде чем убирать правило
plugins/studio/
  .claude-plugin/plugin.json
  agents/      executor, reviewer, designer, scout, assets, reference
  skills/      по папке на команду; setup/steps — шаги нового проекта,
               setup/templates — шаблоны документов (в том числе
               docs/orders/ledger.md) и скрипты проекта (tools/look_sheet.py,
               refs_check.py, asset_check.py, order_api.py)
  reference/   ASKING.md — как спрашивать владельца
  hooks/       hooks.json, guard_git.py, session_context.py, selftest.py
  tools/       env_check.ps1 — проверка компьютера для /setup (не копируется)
```

Нужно на машине: Python в `PATH` (хуки, скрипты); для листов сравнения и
проверки картинок заказов — Pillow (`python -m pip install pillow`; `/setup`
предложит окном; без неё `look_sheet.py` и проверка картинок в
`asset_check.py` выходят с кодом 2); PowerShell для проверки компьютера; для
выкладки — butler (itch.io) или SteamCMD, вход в них владелец делает сам.

Тексты команд намеренно не содержат ничего о конкретном стеке (кроме шагов
`/setup`, которые ставят движок и создают каркас, и площадок `/release`):
игровые шаги (сценарии игрока, площадки, раскрытие ИИ для Steam) в продукте,
который не игра, пропускаются одной строкой. Команды запуска и проверки
живут в `docs/TESTING.md` проекта, стиль — в `docs/orders/` и `docs/refs/`,
правила интерфейса — в `docs/DESIGN.md`, правила кода — в «Правилах проекта»
его `CLAUDE.md`.

## Выпуск плагина

Выпуск самого плагина studio (выпуск игры — `/release`, выше).

1. Поднять `version` в `plugins/studio/.claude-plugin/plugin.json`. Менялись
   шаблоны `skills/setup/templates/` — поднять и метку `шаблон vN` в
   `templates/CLAUDE.md`: по ней `/setup обновить` узнаёт устаревший проект.
2. `python -X utf8 plugins/studio/hooks/selftest.py` — код 0.
3. Обновить описание в `.claude-plugin/marketplace.json` (команды и
   субагенты) и записать версию в `CHANGELOG.md`.
4. `git status`: новые файлы добавить поимённо (`git add
   plugins/studio/skills/release/SKILL.md
   plugins/studio/skills/setup/templates/tools/asset_check.py …`),
   удалённые и переименованные — `git rm` / `git mv`: иначе `hooks.json` и
   скиллы сошлются на файлы, которых нет в репозитории.
5. Коммит, отправка. Затем `/plugin marketplace update claude-game` и сверить
   установленную версию (`/plugin`) с `plugin.json`.
