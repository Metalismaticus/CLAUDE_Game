# CLAUDE_Game — плагин `studio` для Claude Code

Проектный процесс для одного владельца и двух чатов. Вырос из разработки игры
Asterworn и обобщён: годится для игры, приложения, сервиса — любого проекта,
где один человек придумывает и принимает работу, а Claude пишет код.

## Что он делает

- **`/setup`** расспрашивает о замысле (или читает готовый код), **сам
  придумывает, как проверять этот продукт на этом стеке**, разворачивает
  `CLAUDE.md` и `docs/` и ставит первой задачей очереди постройку проверок.
- **Два чата в одной папке.** Чат замысла меняет только `.md` и никогда не
  запускает продукт; чат разработки пишет код руками субагентов. Разделяет их
  не ветка, а то, что каждый трогает.
- **Список — не наряд на работу.** Всё входящее сначала разбирается и встаёт в
  одну очередь в `docs/ROADMAP.md` по влиянию на пользователя.
- **Исполнитель → проверяющий, не больше трёх кругов**, контрольный коммит
  после каждого одобренного пункта; принимает работу только `/done`, непринятое
  откатывается revert-коммитом.
- **Заказы промтом.** Графика, музыка, звук, макеты, тексты: стиль записан один
  раз в `docs/orders/<вид>.md`, заказ собирается из документа, ложится в файл и
  долгом в `BLOCKED.md`. Исполнитель — вручную, OpenAI API или Claude Design.
- **Дизайнер в конвейере.** Пункт с меткой `[ui]` сначала получает спецификацию
  экрана от субагента `designer`, а проверяющий сверяет снимок экрана с ней.

## Установка

```
/plugin marketplace add Metalismaticus/CLAUDE_Game
/plugin install studio@claude-game
```

Обновление: `/plugin marketplace update claude-game`.

Затем в папке проекта — `/setup` (полное имя `/studio:setup`; короткие имена
работают, пока не заняты другой командой).

## Команды

| Команда | Чат | Что делает |
|---|---|---|
| `/setup` | любой, один раз | развернуть процесс в проекте |
| `/idea <заметки>` | замысла | разобрать, проверить по коду, дождаться «да», разнести по документам |
| `/bug <симптом>` | замысла | записать дефект с причиной и строкой «нельзя ломать»; не чинить |
| `/order <вид> <что>` | замысла | собрать заказ, записать долг, отправить исполнителю; `/art`, `/music`, `/design` — короткие формы |
| `/need [раздел]` | замысла | все долги владельца с промтами, готовыми к копированию |
| `/start [пункт\|all]` | разработки | выполнить очередь; «делай» и «делай всё» значат то же |
| `/done [кроме…\|только…]` | разработки | принять партию или её часть, остальное откатить |
| `/add [папка\|design]` | разработки | принять пришедшие файлы заказов и макеты |
| `/check [имя]` | разработки | прогнать проверки и разобрать провалы |
| `/parallel [N\|проверить]` | разработки | предел одновременных пунктов: 0/1 — по одному, 2, 3, 4 …; проверить пробным прогоном |
| `/retro` | разработки | уроки партии: проекту — в документы, процессу — в `docs/PLUGIN-FEEDBACK.md` |
| `/board` | любой | один экран состояния; только чтение |

Субагенты: `executor`, `reviewer`, `designer`, `scout`, `assets`.

## Параллельная работа

`/start all` делает независимые пункты одновременно — каждый в своей копии
проекта (git worktree) — и вливает их в `main` по одному, с проверкой после
каждого. Решает не настройка «вкл/выкл», а разведчик `scout` по каждой партии:
пункты идут вместе, только если их файлы не пересекаются, ни один не трогает
общие узлы (конфигурацию, схему данных, миграции, общие реестры, lock-файлы),
не зависит от другого и не является замером производительности. Сомнение —
по одному.

Сколько пунктов может идти разом — **предел**, настраивается: `/parallel 4`
постоянно, `/start all x4` на один запуск, `/parallel 0` — всё по одному.
Предел — потолок, а не план: при пределе 4 и двух независимых пунктах пойдут
два. `/parallel проверить` гоняет полные проверки в N копиях разом и
записывает наибольшее N, при котором машина не врёт и не тонет.

Как готовить копию под стек проекта, как отделить её данные и какой предел
тянет машина, `/setup` записывает в `docs/TESTING.md` и проверяет на деле. Пока
там не «проверено» — всё идёт по одному, как раньше. Не влилась копия или
проверки начали врать при параллельном прогоне — пункт переделывается по
одному, а партия до конца идёт последовательно.

Ускоряет это код, а не проверку владельцем: выигрыш виден, когда вы ждёте
результат, а не ночью.

## Маршруты пунктов

| Метка | Путь |
|---|---|
| `[код]`, `[баг]` | `executor` → `reviewer` с полной проверкой |
| `[ui]` | `designer` → `executor` → `reviewer` со снимками экрана |
| `[данные]` | `executor` → `reviewer` без полной проверки |

## Исполнители заказов

| Исполнитель | Для чего | Что нужно |
|---|---|---|
| `вручную` | всё | ничего: промт выдаётся одним блоком |
| `api` | графика | `OPENAI_API_KEY` в окружении и Python; платно, отдельно от подписки ChatGPT. Стиль держат приложенные образцы — каждый запрос сам по себе |
| `claude-design` | макеты экранов | настольное приложение с входом в claude.ai. Плагин выгружает дизайн-систему проекта и готовит бриф; **генерацию запускает владелец** — поставить задачу в Claude Design извне нельзя; готовый макет забирает `/add design` |

Ключи и пароли плагин не спрашивает и в файлы не пишет. Автоматика не
сработала — заказ остаётся обычным долгом с готовым промтом.

Не сделано намеренно: заказ через Codex CLI и через автоматизацию веб-интерфейса
ChatGPT. Первое не проверено, второе хрупко и не одобряется правилами сервиса.

## Хук

В проектах, развёрнутых `/setup`, блокируются `git add -A`, `git add --all`,
`git add .` и `git commit -a`: в папке работают два чата, и файлы в коммит
называются поимённо. Нужен Python в `PATH`; без него хук просто молчит.

## Устройство

```
.claude-plugin/marketplace.json
plugins/studio/
  .claude-plugin/plugin.json
  agents/      executor, reviewer, designer, scout, assets
  skills/      по папке на команду; setup/templates — шаблоны документов
  hooks/       hooks.json, guard_git_add.py
```

Тексты команд намеренно не содержат ничего о конкретном стеке: команды
запуска и проверки живут в `docs/TESTING.md` проекта, стиль — в
`docs/orders/`, правила интерфейса — в `docs/DESIGN.md`, правила кода — в
«Правилах проекта» его `CLAUDE.md`.
