# 3. Выполнить один пункт

Глава протокола `/start` — читать, дойдя до этого этапа; после сжатия контекста перечитать. Пути — от базовой папки скилла (там лежит `SKILL.md`), как в нём; «раздел N» — глава `steps/N.md`.

Волна из одного пункта — здесь, в основной папке, **строго по одному агенту за
раз**: папка и данные продукта общие. Волна из нескольких — раздел 3а; `[вид]`
в обоих — шагами 3б. Волны идут по порядку: следующая — когда предыдущая
целиком влита или снята (`[вид]` после слияния основы — 3а).

1. Отметить пункт `в работе · круг 1/3 · с <дата ЧЧ:ММ>` (начало пункта, не шага).
2. **`[ui]`** — сначала свежий `designer`: «Пункт N партии из
   `docs/BATCH.md`, спецификацию записать в `docs/specs/<дата>-N-<экран>.md`».
   Его итог: «Решено за вас» — к пункту с пометкой `дизайн:`; «В DESIGN.md
   при /done» — в «В документы при `/done`» с префиксом `DESIGN:`; «Вопрос
   владельцу» — раздел 4, `executor` не звать.
3. Свежий `executor`, сообщение — одна строка: «Пункт N партии из
   `docs/BATCH.md`», для `[ui]` — путь спецификации, для `[вид]` — шаг и
   полный путь библиотеки приёмов `../../reference/LOOK_TECHNIQUES.md` (от
   базовой папки скилла; без него исполнитель найдёт только пустой
   `docs/refs/TECHNIQUES.md` проекта); есть у `scout` строка «Карта чтения
   пункта N: открыть — …; не открывать — …» — её дословно (исполнитель идёт
   по ней, не по всему проекту); в
   партии уже влита уборка общего узла — ещё её строка «В документы при
   /done» о том, как теперь добавлять (проверку, вид содержимого): документы
   правит только `/done`. Больше ничего не пересказывать. **Пункт-замер**
   (его итог — числа: проба стека или рендера, цена эффекта; `scout` ставит
   его одного) — без окна (пару кадров пробы судит `/done`, раздел 6); занят
   (п. 1 «Замеров» раздела 6) — числа с пометкой, как в п. 3 там.
4. «ждёт» или «не удалось» — раздел 4.
5. «готово» — записать к пункту «Как увидеть» и «Решено за вас» из итога,
   итог целиком — в `../<папка проекта>.wt/rounds/p<N>-r<R>-итог.md`, и
   запустить свежего `reviewer`: номер пункта, метка маршрута, круг R/3, режим
   (по «Главному»), для `[ui]` — путь спецификации, для `[вид]` — шаг, путь
   паспорта, тот же полный путь библиотеки приёмов и строку «Лист», «Файлы»
   и «Как увидеть» из итога, строку «как
   теперь добавлять» влитой уборки общего узла (как исполнителю), строку
   «Карта чтения» `scout`, если есть; путь к
   итогу — последней строкой.
6. `CHANGES_REQUESTED` — `в работе · круг R/3` (после третьего — раздел 4).
   Снять файлы пункта в `…/rounds/p<N>-r<R>/` (`cp --parents <файлы>
   <туда>`). Новый `executor` — прежнее сообщение (для копии — без
   «подготовь») и замечания дословно — из четырёх частей, как их пишет
   проверяющий (`[основание] файл:строка — что не так — готово, когда:
   <признак>`), «исправить ровно до «готово, когда», только их»; замечание без
   файл:строка — не замечание (вкус — «Вне круга»), исполнителю не передавать.
   **Две правки подряд воспроизвели тот же дефект** — прежде третьего
   `executor` координатор читает последний итог (`rounds/p<N>-r<R>-итог.md`)
   и называет в сообщении, почему гипотеза не сработала и что меняется;
   список указаний не наращивать. У `[вид]` это — смена способа: где
   «Вижу:» двух кругов подряд называют тот же главный дефект, — ещё «<дефект>
   два круга — это способ, не числа: возьми следующий приём из строки «У нас:»
   или «Как сделано у образца» паспорта, назови «меняю способ: <приём> →
   <приём>, потому что …»» (одна смена на выбор K; дальше — 3б, п. 5). Новый
   `reviewer` — **узкая повторная проверка**: сообщение
   п. 5, прошлые замечания дословно и путь к diff правки (`git diff
   --no-index` снятых файлов с нынешними, новый — с `/dev/null`)
   `…/rounds/p<N>-r<R+1>.diff`.
7. `APPROVED` — «Файлы» итога сверить с `git status`, не считая `.md`,
   `docs/refs/` (там пишет и чат замысла) и чужого со старта (раздел 1, п. 1);
   расходится — свежий `executor`: «итог не сходится с диском: <файлы> —
   включи в «Файлы» или верни», затем `reviewer`; снова — `не выполнен`.
   Сошлось — `готов к проверке · одобрен на круге R/3` (у `[вид]` — только
   после встраивания, до него — следующий шаг 3б); к «Как увидеть» — пути
   снимков и «Не судил»; в «В документы при `/done`» — строки исполнителя, его
   `Ловушка:` и `Ограничение:` проверяющего (кроме лёгкого режима — его
   закроет полная в конце); «Замечено вне пункта» и «Вне круга» — в «Найдено
   по ходу» (строку «решил сам» проверяющего — в «Принято по умолчанию»).
   Контрольный коммит — файлы итога поимённо (и спецификация `[ui]`); первая
   строка — «Коммит» итога (`Пункт N: …`; не по правилам — переписать по «Как
   увидеть»; у шагов 3б «стенд», «основа», «выбор K» — постоянное сообщение
   из `COMMITS.md`, у «основы» что изменилось — из «Коммита» итога), тело —
   «Как увидеть» на языке коммитов без путей к `.wt/shots` и числа проверок;
   `git log -1 --format=%s` начинается с `Item N:` / `Пункт N:`; затем
   `docs/BATCH.md`: `Партия: пункт N готов к проверке`.
8. Отправить, если в `CLAUDE.md` контрольные коммиты отправляются. Push
   отклонён — `git fetch` и `git merge --no-edit origin/<ветка>` (не `pull
   --rebase`: мешают `.md` чата замысла), проверка пункта и снова отправить;
   конфликт — остановиться и описать.
