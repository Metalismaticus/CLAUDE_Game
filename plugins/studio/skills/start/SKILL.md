Что запускаем: **$ARGUMENTS**

(Если строка выше пуста или осталась без подстановки — аргумент взять из
сообщения владельца; нет и там — это пустой `/start`.)

`/start` без аргумента берёт первый доступный пункт из «Очереди» в
`docs/ROADMAP.md`, `/start <название>` — названный пункт, `/start all` — все
доступные пункты текущей очереди в порядке их значимости.

`/start all x4` или «делай всё в 4 потока» — предел одновременных пунктов **на
этот запуск** вместо записанного в `docs/TESTING.md`; `x1` — всё по одному.
Постоянный предел меняет `/parallel`.

Работа идёт в основной папке на основной ветке, рядом с чатом замысла. Чат
замысла меняет только `.md`, этот чат — код, данные, ассеты, проверки и
`docs/BATCH.md` (`CLAUDE.md`, «Два чата»). Чат, в котором звали `/start`, дальше
считается чатом разработки: «делай» в нём равно `/start`.

**Этот чат — координатор.** Код сам не читает и не пишет, логи и вывод проверок
в контекст не тянет. Пункт делает свежий субагент `executor`, до коммита его
проверяет свежий `reviewer`; пункту `[ui]` сначала пишет спецификацию
`designer`; независимые пункты идут одновременно, если так решил разведчик
`scout`. Субагенты плагина зовутся инструментом Agent как `studio:executor`,
`studio:reviewer`, `studio:designer`, `studio:scout`, `studio:assets`; если
такого типа нет — без префикса. Координатор выбирает пункты, ведёт
`docs/BATCH.md`, коммитит и отчитывается.

Нет `docs/ROADMAP.md` — проект не развёрнут: предложить `/setup` и остановиться.

## 1. Подготовить основу

1. Проверить `git status` и текущую ветку. Ветка не та, что названа в
   `CLAUDE.md` («Два чата»), — остановиться и спросить владельца.
2. Чужие незакоммиченные изменения не трогать и в свои коммиты не брать.
   Незакоммиченные `.md` — это нормально, их пишет чат замысла. Незнакомые код
   или ресурсы — сначала описать владельцу.
3. **Пришедшие файлы заказов — первыми, и не своими руками.** Если в папках
   назначения из паспортов `docs/orders/*.md` есть файлы, которых нет в git,
   запустить субагента `assets` с одной строкой: «Разбери пришедшее по
   инструкции `<путь>`», где путь — `../add/SKILL.md` относительно базовой
   папки этого скилла. Сам координатор картинки не открывает и промты не читает.
   От агента приходит короткий итог. В текущую партию пришедшее не попадает.
4. Прочитать `docs/BATCH.md`. Партия там уже есть — продолжить её, новую не
   снимать.

## 2. Зафиксировать объём

Перечитать «Очередь» в `docs/ROADMAP.md`: чат замысла мог её поменять.

- Для обычного `/start` выбрать ровно один пункт.
- Для `/start all` один раз снять список всех пунктов с меткой `[можно]`.
  Найденное по ходу — в `docs/BATCH.md`, раздел «Найдено по ходу», и в отчёт
  владельцу, но партию им не расширять.
- Названный пункт заблокирован вопросом, файлом или проверкой владельца —
  объяснить это и взять другой только при пустом `/start` или `/start all`.
- Не брать две задачи, меняющие одни и те же файлы или правила, как
  независимые.
- У пункта нет метки маршрута — определить её по описанию и записать в партию:
  видимое пользователю — `[ui]`; только файлы содержимого без кода —
  `[данные]`; иначе `[код]`.

**Волны.** Предел — из аргумента запуска (`xN`), иначе из `docs/TESTING.md`.
В партии больше одного пункта, параллельная работа «проверено» и предел больше
1 — запустить свежего `scout` с номерами пунктов и пределом и взять его волны
как есть. Предел из аргумента выше проверенного — одной строкой сказать об этом
в отчёте; при состоянии «не проверено» аргумент параллельность не включает:
копия не готова. Иначе каждый пункт — своя волна, и всё идёт
по одному, как раньше. Решение `scout` координатор не расширяет: пары, которую
он не предложил, не собирать.

Записать партию в `docs/BATCH.md` по образцу из его шапки: номер, волна, пункт с
метками, критерий готовности, состояние; строкой над таблицей — волны и почему
пункт идёт один. Номера стабильные — на них ссылается
`/done кроме 3`. Пункты, которые чат замысла поставит в очередь после этого
снимка, относятся к следующему запуску.

Партия может задеть данные пользователя из `docs/TESTING.md` — снять копию, как
там сказано, и записать это в `docs/BATCH.md`: владелец проверяет партию на
живых данных.

До первого пункта выполнить исходную проверку: для `/start all` — полную, для
одного пункта — быструю (команды из таблицы `docs/TESTING.md`). Иначе нельзя
понять, какой пункт сломал последующий прогон. В контекст брать только итоговую
строку. Состояние полигона не «есть» — выполнить то, что есть, и записать в
партию, чем ограничена проверка. Красная основа — остановиться и показать
провал, если только это не намеренно красная проверка из `docs/BUGS.md`.

## 3. Выполнить один пункт

Волна из одного пункта — этот раздел, в основной папке. Волна из нескольких —
раздел 3а. Волны идут по порядку: следующая начинается, когда предыдущая
целиком влита или снята.

В основной папке — **строго по одному агенту за раз**: папка и данные продукта
у всех общие:

1. Отметить пункт в `docs/BATCH.md` как `в работе`.
2. **Пункт `[ui]`** — сначала свежий `designer`: «Пункт N партии из
   `docs/BATCH.md`, спецификацию записать в `docs/specs/<дата>-N-<экран>.md`».
   Итог с вопросом владельцу — раздел 4, как «ждёт».
3. Запустить свежего `executor` и ждать ответа. Сообщение — одна строка:
   «Пункт N партии из `docs/BATCH.md`», для `[ui]` — ещё путь спецификации.
   Больше ничего не пересказывать: всё нужное он прочитает сам.
4. Итог «ждёт» или «не удалось» — раздел 4.
5. Итог «готово» — запустить свежего `reviewer`: номер пункта, метка маршрута,
   строка «Файлы» из итога исполнителя, для `[ui]` — путь спецификации.
6. `CHANGES_REQUESTED` — новый `executor`: номер пункта и замечания
   проверяющего дословно, «исправить только их». Потом снова новый `reviewer`.
   Не больше **трёх кругов** «исполнитель → проверяющий»; не одобрено за три —
   раздел 4.
7. `APPROVED` — в `docs/BATCH.md` отметить `готов к проверке` и записать к
   пункту строки «В документы при /done» и «Свои числа» из итогов, а также
   строку «Ограничение» проверяющего, если она была. Один контрольный коммит:
   файлы из итога поимённо (спецификация `[ui]` — тоже) и `docs/BATCH.md`,
   никогда `git add -A` или `git add .`; сообщение — строка «Коммит» из итога,
   она начинается с `Пункт <номер>:` — по нему `/done` найдёт коммиты пункта.
   Файл из итога, которого нет в `git status`, или изменённый файл вне итога —
   остановиться и спросить исполнителя, а не угадывать.
8. Отправить, если в `CLAUDE.md` сказано, что контрольные коммиты
   отправляются. Push отклонён — `git pull --rebase`, прогнать проверку пункта
   и отправить снова; конфликт — остановиться и описать.

Контрольный коммит — сохранение и точка отката, а не принятие: принимает только
`/done`, непринятое он откатит.

Документы, кроме `docs/BATCH.md` и спецификаций в `docs/specs/`, во время партии
не править ни координатору, ни агентам: что в них поменять, записано к пункту —
внесёт это `/done`.

## 3а. Волна: пункты одновременно

Каждый пункт волны работает в **своей копии проекта** — git worktree на своей
ветке, вне основной папки. Основная папка и `main` не меняются, пока пункт не
одобрен; владелец и чат замысла ничего не замечают.

**Запуск.**

1. Для каждого пункта N волны от текущего `main`:

   ```bash
   git worktree add "../<имя папки проекта>.wt/p<N>" -b "wave/p<N>" main
   ```

2. Запустить всех `executor` волны **одновременно** (несколько вызовов Agent в
   одном сообщении). Сообщение каждому: «Пункт N партии из `docs/BATCH.md`.
   Работай только в копии `<полный путь копии>`: сначала подготовь её по
   `docs/TESTING.md`, «Параллельная работа»». Пунктам `[ui]` спецификацию
   до этого пишет `designer` в основной папке — всем пунктам волны
   одновременно: каждый пишет только свой файл в `docs/specs/`.
3. Каждый итог «готово» — свежий `reviewer` для этого пункта с тем же путём
   копии, не дожидаясь остальных. Круги «исполнитель → проверяющий» у каждого
   пункта свои, не больше трёх.
4. `docs/BATCH.md` ведётся **только в основной папке** и только координатором:
   в копиях его не править и не коммитить — иначе слияния поссорятся.

**Слияние — строго по одному, в порядке очереди**, по мере одобрения:

1. В копии: коммит файлов пункта поимённо, сообщение из итога — `Пункт N: …`.
2. В копии: `git rebase main`. Конфликт — `git rebase --abort`; пункт не
   чинить вслепую, а отправить в раздел «Сбой волны».
3. Rebase прошёл, а `main` успел измениться — в копии быстрая проверка и
   проверка пункта; красное — «Сбой волны».
4. В основной папке: `git merge --ff-only wave/p<N>` — в `main` ложатся те же
   коммиты `Пункт N: …`, по ним `/done` найдёт и откатит пункт.
5. В основной папке — быстрая проверка. Красное — откатить коммиты пункта
   (`git revert --no-edit`), «Сбой волны».
6. Отметить в `docs/BATCH.md` `готов к проверке` со строками из итогов и
   закоммитить его отдельно, сообщением `Партия: пункт N готов к проверке` (не
   `Пункт N:` — этот коммит `/done` не откатывает).
7. Отправить, если в `CLAUDE.md` коммиты отправляются.
8. Убрать копию: `git worktree remove <путь>` и `git branch -d wave/p<N>`.

После последнего слияния волны — полная проверка в основной папке. Проверки из
«Нельзя одновременно» гонять только здесь, по одной.

**Сбой волны.** Пункт, который не влился, не проиграл, а просто оказался не
таким независимым, как обещал прогноз:

- вернуть его в партию `ждёт очереди` с пометкой «повтор по одному: <причина>»
  и выполнить **после** волны по разделу 3, в основной папке, с нуля — копию
  и ветку удалить (`git worktree remove --force`, `git branch -D`);
- записать в «Найдено по ходу», что `scout` ошибся и в чём: если причина — не
  названный общий узел, это строка для `docs/TESTING.md`, «Общие узлы».

**Ложные провалы.** Проверка краснеет в копии и зеленеет одна в основной
папке — параллельность вредит прогонам. До конца партии всё по одному; в
«Найдено по ходу» — предложение снизить предел или дописать «Нельзя
одновременно».

## 4. Ошибка или блокировка внутри `all`

- Итог «ждёт» — отметить `ждёт`, записать точный вопрос из итога и продолжить
  следующий независимый пункт.
- Итог «не удалось» или три круга без одобрения — вернуть **только
  незакоммиченные изменения файлов из итога исполнителя**: изменённые —
  `git checkout -- <файлы>`, созданные пунктом — удалить. Отметить
  `не выполнен` с последними замечаниями проверяющего и продолжить.
- Если изменения пункта нельзя безопасно отделить или сломалась общая основа —
  остановить всю партию. Не продолжать поверх неизвестно красного состояния.

При откате не трогать файлы, которых пункт не менял: там может лежать работа
чата замысла.

## 5. Поправки после проверки владельца

Владелец посмотрел пункт и просит поправить — тот же цикл раздела 3: новый
`executor` с номером пункта и словами владельца дословно, затем `reviewer`,
затем коммит `Пункт <номер>: поправка — …`. Поправка **по виду** у пункта `[ui]`
сначала идёт `designer`: он правит спецификацию и выносит в итог правило для
`docs/DESIGN.md` — поправка, сделанная дважды, значит, что правила не хватает.
В `docs/BATCH.md` дописать к пункту, что поправлено.

## 6. Завершить запуск

После всей партии — полная и долгая проверки и быстрая, в контекст только
итоговые строки. После одного пункта отдельного прогона не нужно: полный уже
сделал проверяющий. Нужен разбор провала — отдать его свежему `reviewer`, а не
читать вывод самому. Теги не ставить: это делает `/done`.

Остались копии в `../<имя папки проекта>.wt/` — перечислить их, а не удалять
молча: там может быть незакоммиченная работа.

Выдать отчёт с номерами из `docs/BATCH.md`: волны и что шло одновременно,
сбои волн, сделано, пропущено, не выполнено,
вопросы, хеши коммитов, чем ограничена проверка (если полигон не «есть»),
копия данных пользователя, если делалась. Для `[ui]` — пути снимков.
Последняя строка обязательна:

> Проверьте результат в продукте. Для принятия всей партии вызовите `/done`,
> либо `/done кроме ...` или `/done только ...` для выбранных пунктов.
