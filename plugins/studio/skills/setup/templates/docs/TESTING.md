### Правила каркаса

- проверка без единого утверждения — провал;
- ошибка скрипта во время проверки — провал, если её явно не разрешили;
- пропуск — только с причиной;
- пустой вывод или ненайденный движок — красное;
- итог перечисляет каждый провал поимённо;
- раннер находит проверки сам: новая проверка — новый файл, без строки в
  общем списке; общие помощники проверок — в одной папке (`tests/lib/`), не
  копиями по файлам;
- у каждой команды предел времени (замер × 3), зависание — красное (код 124).

## Сценарии игрока

Для игры; продукт не игра — раздел одной строкой «не нужен: <почему>».

Пункт про управление, интерфейс или действия игрока проверяется сценарием
через ввод: он нажимает, как игрок, а не вызывает функцию. Раннер сценариев —
часть полигона, команда — строка «сценарий игрока» в «Командах проверки».
Сценарий — файл данных `tests/scenarios/<имя>.json` {{или ресурс движка того же
смысла: …}}: точка входа (сцена или уровень), зерно, фиксированный шаг времени,
шаги. Пример (Godot):

```json
{
  "entry": "res://main.tscn",
  "seed": 1,
  "fps": 60,
  "steps": [
    {"press": "кнопка:Новая игра", "frame": 30},
    {"wait_for": "Player", "timeout": 120},
    {"press": "move_forward", "hold": 60},
    {"wait_frames": 70},
    {"assert": "Player.position.z", "max": -2.0},
    {"press": "jump", "hold": 10},
    {"assert": "Player.position.y", "min": 2.6, "within": 60},
    {"assert": "group:enemies.count", "min": 1},
    {"assert": "текст:Уровень 1", "equals": true},
    {"shot": "first-steps"}
  ]
}
```

- Время — в кадрах при фиксированном шаге (`fps`), не в секундах.
- `press` — действие ввода из настроек управления или `кнопка:<текст>`: кнопку
  интерфейса нажимают по тексту, не по координатам; `frame` — кадр от начала
  сценария (нет — сразу); `hold` — сколько кадров держать, следующие шаги
  идут, пока держится.
- `wait_for` — узел, объект или `текст:<строка>` на экране; не дождался за
  `timeout` кадров — провал.
- `assert` — по именам и группам объектов (`Player.position.z`,
  `group:enemies.count`) или `текст:<строка>` на экране; `equals`, `min`, `max`.
  Без поля — на текущем кадре; `"within": N` — зелено, если условие выполнилось
  хоть на одном из следующих N кадров (вершина прыжка); `"always": N` — на
  каждом из них (не падает, не уходит за край).
- `shot` — снимок кадра с этим именем в папку снимков, названную раннеру.
- Коды: 0 — зелено; 1 — провал: какое утверждение, на каком кадре, какие
  действия остались зажаты; 2 — плохой сценарий (нет файла, неизвестный шаг
  или действие).
- Полная проверка и группа `сценарии` прогоняют все `tests/scenarios/*.json`,
  провалы — поимённо: так сценарий ядра стережёт управление и от следующих
  пунктов.

«Готово, когда» пункта, записанное шагами игрока, — текст сценария: шаги и
числа берутся оттуда.

## Стенд

Место, где 2–4 варианта пункта показываются владельцу одинаково раз за разом,
чтобы он выбрал. Две части, у каждой своё состояние: «вид» — для `[вид]`
(стенд вида), «ощущение» — для `[ощущение]` (стенд ощущения). Пока нужная
часть не «есть», пункт начинается с её постройки. Ненужная часть — «не нужна:
<почему>»: вид — продукту без мира (только экраны), ощущение — без управления
и камеры.

### Вид

**Состояние: {{нет | строится | есть | не нужна: …}}**

Варианты снимаются рядом с образцом на одних и тех же кадрах:

- отдельная сцена или режим запуска: {{…}};
- именованные кадры: камера ставится по имени кадра из паспорта
  `docs/refs/<тема>.md` («Кадры»);
- время и ветер остановлены — два снимка одного кадра одинаковы;
- пресеты света: нейтральный и целевой;
- вариант включается аргументом (`A`, `B`, `C` …), пресет графики — тоже
  (`--пресет низкие|высокие`);
- для масштаба в кадре — капсула 1,8 м и куб 1 м;
- движок проверяет, что объект в кадре, иначе снимок — ошибка;
- место владельца снимается по seed и координатам из записи бага или «Как
  увидеть»: по клавише (F3) игра показывает seed, координаты и направление
  камеры и копирует их одной строкой, этой строкой стенд ставит камеру.

Команда — строка «снимок кадра» в «Командах проверки». Лист сравнения —
`python tools/look_sheet.py --ref <образец> --var A=<снимок> [--var B=…]
--out docs/refs/<тема>/sheet-<дата>.png --json <файл>` (нужна Pillow; код 2 —
её нет). Картинки образцов на месте — `python tools/refs_check.py`, код 0.
Каждый снимок до строки «Вижу:» — строка «кадр не пустой» в «Командах
проверки» (`look_sheet.py --sanity`; варианты — через `--var`, снимок
прошлого круга — `--prev <кадр>=<прошлый>`; два одинаковых снимка стенда без
`--var` не брак — это проверка повторяемости): код 1 — брак без обсуждения.
Числа листа — опора, а не приёмка: первым судится главное впечатление
паспорта.

## Бюджет пункта

Пункт не тянется часами. Кроме кругов (не больше трёх на шаг) у него есть
время — чистая работа агентов от начала пункта (время начала — в его строке
`docs/BATCH.md`), без ожидания владельца:

| Размер пункта | Бюджет |
|---|---|
| малый | ~1 ч |
| средний (размер не указан) | ~2 ч |
| большой | ~4 ч |

Размер — строка «Размер:» пункта в «Подробностях» `docs/ROADMAP.md`; нет её
— средний. Числа — выбор проекта, владелец их может поправить здесь.

Стоп без окна — вышел бюджет или два круга подряд без видимого сдвига
(строки «Вижу:» называют тот же главный дефект, менялись только числа): в
первый раз — смена способа по паспорту, после неё снова без сдвига — пункт
`не выполнен: не уложился — <что видно, что пробовали, чем способ плох>`,
работа — в `rounds/`, строка «Найдено по ходу» для `/idea` (другой приём,
образец или размер); партия идёт дальше. В отчёте конца запуска такие
пункты — первыми, с «Вижу:» последнего круга и строкой «что предлагаю».

## Параллельная работа

**Состояние: {{не проверено | проверено | невозможно}} · пишут: {{1}} · тяжёлых проверок: {{1}}**

`/start` делает независимые пункты одновременно, каждый в своей копии проекта
(git worktree), только при состоянии «проверено» и `пишут` больше 1. Решает по
пунктам разведчик `scout`; сомнение — по одному.

- `пишут` — сколько пунктов пишется одновременно: 0 или 1 — всё по одному; 2,
  3, 4 … — до стольких разом. `/parallel N`, на один запуск — `/start all xN`.
- `тяжёлых проверок` — сколько полных и долгих прогонов и проверяющих со
  снимками стенда идёт одновременно, обычно 1: в `/start all` проверяющие
  пунктов работают в лёгком режиме, а полная и долгая идут один раз, в
  основной папке в конце партии. `/parallel проверки M`.
- Проверить числа пробным прогоном — `/parallel проверить`.

### Как мерить — группа «замеры»

- **Что мерить**: время каждого кадра; CPU рендера и GPU раздельно (Godot:
  `RenderingServer.viewport_set_measure_render_time(rid, true)`, затем
  `viewport_get_measured_render_time_cpu(rid)` + `get_frame_setup_time_cpu()`
  и `viewport_get_measured_render_time_gpu(rid)`; другой движок — узнать у
  движка, как он отдаёт время CPU и GPU кадра); наш код — своими таймерами. В
  итоге — p50/p95/p99, максимум, число рывков и предел: CPU или GPU.
  `Engine.get_frames_per_second()`, `TIME_FPS`, `TIME_PROCESS` и средний FPS
  в утверждения не брать: они за секунду, фриз в 100 мс в них не виден.
- **Предпроверка** — не прошла: «замер не состоялся: <причина>», код 3, не
  красное; с `--занят` занятость (ниже) — пометка «занят: <чем>», не код 3. Основная папка, не копия; других процессов движка нет; процессор
  свободен — ≤ 10% за 3 с без процессов сборки проекта (`dotnet`,
  `VBCSCompiler`, `MSBuild`; их сначала подождать, до 30 с); видеокарта
  свободна — сумма `engtype_3D` по процессам, кроме `dwm`, приложения Claude и
  самого замера, ≤ 5% за 3 с (Windows:
  `Win32_PerfFormattedData_PerfOS_Processor` и
  `Win32_PerfFormattedData_GPUPerformanceCounters_GPUEngine` — от языка ОС не
  зависят); питание от сети; окно видно и в фокусе (перекрытое Windows
  замедляет); vsync выключен; C# оптимизирован — экспортированная сборка
  (`ExportRelease`), а пока шаблонов экспорта нет — сборка редактора
  `dotnet build <csproj> -p:Optimize=true` (редактор грузит только Debug, а
  свойство из командной строки перекрывает `Optimize=false` Godot.NET.Sdk);
  конфигурация — в базу (`csharp: Debug+Optimize` | `ExportRelease`), разные
  не сравнивать. Шаблоны экспорта ставятся только по «да» владельца
  окном.
- **Прогон**: прогрев ≥ 5 с и пока растёт компиляция шейдеров (Godot —
  `Performance.PIPELINE_COMPILATIONS_*`; рендер без этих счётчиков, как
  `gl_compatibility`, — первый прогон целиком прогрев и выбрасывается, рывки
  — медиана 5 прогонов); маршрут — по кадрам (`--fixed-fps 60`), а не по
  реальному времени, ≥ 1000 кадров после прогрева; мерить **во время
  подгрузки** мира, а не после неё; разрешение — уровня (экран 1080p — во
  весь экран), иначе GPU-часть пересчитать по числу пикселей.
- **Пробный режим** (`--проба`: 1 прогон, 1 пресет, без предпроверки, порогов
  и базы, `--quit-after`) — им проверяющий убеждается, что пункт, менявший
  группу, не сломал её скрипт; числа пробы не судят.
- **Компьютер занят** (процессор, видеокарта, другой процесс движка, окно
  не в фокусе) — `/start` в конце партии мерит всё равно, без окна, с
  `--занят`: итог «сняты на занятом компьютере (<чем>) — числа могут быть
  хуже настоящих», базу такой прогон не снимает и не меняет, «хуже базы» —
  не красное, а «перепроверить при следующем замере». Зонд со временем
  кадра (проба стека, цена эффекта) — так же, число с той же пометкой.
- **Каждый пресет графики** — свой прогон и своя цель: низкие → минимальный,
  высокие → рекомендуемый, ультра (нет — самый высокий) → машина владельца.
  Настроек графики ещё нет — один прогон на цель рекомендуемого.
- `[вид]` и `[ощущение]`, у которых есть цена в кадре: исполнитель и
  проверяющий пишут, на каком пресете что проверено.

### Регрессии

База — `tests/perf/baselines/<id машины>/<сценарий>.json`: отпечаток, движок,
рендерер, сборка C#, пресет, окно, коммит, дата; 5 прогонов, по метрике —

подтвердил. Базы нет — первый прогон группы её снимает. Отпечаток сменился

новую базу, прежнюю хранит рядом (`<сценарий>.<дата>.json`), в итог —

пересъём — только `/check замеры пересъём` по слову владельца, не сразу
после красного: иначе база узаконит регрессию.
