### Правила каркаса

- проверка без единого утверждения — провал;
- ошибка скрипта во время проверки — провал, если её явно не разрешили;
- пропуск — только с причиной;
- пустой вывод или ненайденный движок — красное;
- итог перечисляет каждый провал поимённо;
- у каждой команды предел времени (замер × 3), зависание — красное (код 124).

### Красное, которое бывает правильным

## Сценарии игрока

Для игры; продукт не игра — раздел одной строкой «не нужен: <почему>».

Пункт про управление, интерфейс или действия игрока проверяется сценарием
через ввод: он нажимает, как игрок, а не вызывает функцию. Раннер сценариев —
часть полигона, команда — строка «сценарий игрока» в «Командах проверки».
Сценарий — файл данных `tests/scenarios/<имя>.json` {{или ресурс движка того же
смысла: …}}: точка входа (сцена или уровень), зерно, фиксированный шаг времени,
шаги. Пример (Godot):

```json
{
  "entry": "res://main.tscn",
  "seed": 1,
  "fps": 60,
  "steps": [
    {"press": "кнопка:Новая игра", "frame": 30},
    {"wait_for": "Player", "timeout": 120},
    {"press": "move_forward", "hold": 60},
    {"wait_frames": 70},
    {"assert": "Player.position.z", "max": -2.0},
    {"press": "jump", "hold": 10},
    {"assert": "Player.position.y", "min": 2.6, "within": 60},
    {"assert": "group:enemies.count", "min": 1},
    {"assert": "текст:Уровень 1", "equals": true},
    {"shot": "first-steps"}
  ]
}
```

- Время — в кадрах при фиксированном шаге (`fps`), не в секундах.
- `press` — действие ввода из настроек управления или `кнопка:<текст>`: кнопку
  интерфейса нажимают по тексту, не по координатам; `frame` — кадр от начала
  сценария (нет — сразу); `hold` — сколько кадров держать, следующие шаги
  идут, пока держится.
- `wait_for` — узел, объект или `текст:<строка>` на экране; не дождался за
  `timeout` кадров — провал.
- `assert` — по именам и группам объектов (`Player.position.z`,
  `group:enemies.count`) или `текст:<строка>` на экране; `equals`, `min`, `max`.
  Без поля — на текущем кадре; `"within": N` — зелено, если условие выполнилось
  хоть на одном из следующих N кадров (вершина прыжка); `"always": N` — на
  каждом из них (не падает, не уходит за край).
- `shot` — снимок кадра с этим именем в папку снимков, названную раннеру.
- Коды: 0 — зелено; 1 — провал: какое утверждение, на каком кадре, какие
  действия остались зажаты; 2 — плохой сценарий (нет файла, неизвестный шаг
  или действие).
- Полная проверка и группа `сценарии` прогоняют все `tests/scenarios/*.json`,
  провалы — поимённо: так сценарий ядра стережёт управление и от следующих
  пунктов.

«Готово, когда» пункта, записанное шагами игрока, — текст сценария: шаги и
числа берутся оттуда.

## Стенд

Место, где 2–4 варианта пункта показываются владельцу одинаково раз за разом,
чтобы он выбрал. Две части, у каждой своё состояние: «вид» — для `[вид]`
(стенд вида), «ощущение» — для `[ощущение]` (стенд ощущения). Пока нужная
часть не «есть», пункт начинается с её постройки. Ненужная часть — «не нужна:
<почему>»: вид — продукту без мира (только экраны), ощущение — без управления
и камеры.

## Параллельная работа

**Состояние: {{не проверено | проверено | невозможно}} · пишут: {{1}} · тяжёлых проверок: {{1}}**

`/start` делает независимые пункты одновременно, каждый в своей копии проекта
(git worktree), только при состоянии «проверено» и `пишут` больше 1. Решает по
пунктам разведчик `scout`; сомнение — по одному.

- `пишут` — сколько пунктов пишется одновременно: 0 или 1 — всё по одному; 2,
  3, 4 … — до стольких разом. `/parallel N`, на один запуск — `/start all xN`.
- `тяжёлых проверок` — сколько полных и долгих прогонов идёт одновременно,
  обычно 1: в `/start all` проверяющие пунктов работают в лёгком режиме, а
  полная и долгая идут один раз, в основной папке в конце партии.
  `/parallel проверки M`.
- Проверить числа пробным прогоном — `/parallel проверить`.

### Набор копий

Копии — `../<папка проекта>.wt/slot<K>`, по одной на пишущий пункт. Первый
раз слот создаётся (`git worktree add -b wave/p<N> <slot> main`) и готовится
по «Подготовке копии», дальше переиспользуется между волнами партии:

```bash
git -C <slot> reset --hard
git -C <slot> clean -fd
git -C <slot> checkout -B wave/p<N> main
```

`clean` без `-x` не трогает файлы из `.gitignore` — подготовленные кэши,
зависимости и локальная настройка копии остаются, если они там; всё, что
кладёт подготовка, должно быть в `.gitignore`. Страж коммитов разрешает
`reset --hard` и `clean` только в копиях `*.wt/…`. Что повторить в
переиспользованной копии, если менялись зависимости или ресурсы: {{… или
«ничего»}}.
